# Functional specification

- Feature ID: FEATURE-002
- Revision: 2

- Author role: Product agent

## Goal

Добавить отдельный режим «На время», в котором пользователь в течение фиксированных 60 секунд последовательно решает неограниченное заранее количество примеров: после каждого принятого ответа сразу показывается следующий пример. Сессия автоматически завершается по дедлайну, после чего показывается итоговый результат.

## Non-goals

- Ограничение timed-сессии десятью примерами.
- Настраиваемая длительность.
- Пауза, продление или восстановление timed-сессии после reload.
- Изменение математических пулов FEATURE-001.
- Backend, аккаунты, история результатов, рейтинги.
- Изменение обычного режима кроме выбора режима до старта.

## Actors and permissions

- **Школьник** — выбирает класс и режим, запускает сессию, вводит ответы, видит итог.
- **Родитель/учитель** — отдельной роли и прав нет; может только наблюдать экран результата.
- Аутентификация отсутствует.

## Glossary

- **Обычный режим** — существующая FEATURE-001 сессия из 10 заданий без общего таймера.
- **Timed-режим** — новая сессия фиксированной длительности 60 секунд без заранее заданного количества задач.
- **Дедлайн** — момент `startedAt + 60 000 ms`.
- **Принятый ответ** — submit, обработанный строго до дедлайна.
- **Решено** — количество принятых ответов, независимо от правильности.
- **Правильно** — количество принятых ответов, совпавших с правильным ответом задачи.

## User scenarios

### Main scenarios

**SCENARIO-001 — Непрерывное решение до таймаута**
1. Пользователь выбирает класс и режим «На время».
2. После успешного старта показывается первый пример и начинается отсчет 60 секунд.
3. Пользователь отправляет ответ.
4. Если дедлайн еще не достигнут, приложение принимает ответ и немедленно показывает следующий пример.
5. Шаги 3–4 повторяются столько раз, сколько пользователь успеет за 60 секунд.
6. При достижении дедлайна приложение автоматически завершает сессию и показывает результат.

**SCENARIO-002 — Таймаут при введенном, но не отправленном ответе**
- Введенное значение отбрасывается; оно не увеличивает количество решенных и не влияет на количество правильных.

### Alternative and negative scenarios

**SCENARIO-003 — Submit на границе дедлайна**
- Если в момент обработки submit `now >= deadline`, ответ не принимается и выполняется завершение по таймауту.

**SCENARIO-004 — Browser throttling / background tab**
- Визуальные тики могут задерживаться, но дедлайн не переносится; при следующем выполнении приложение сравнивает текущее время с абсолютным дедлайном.

**SCENARIO-005 — Reload**
- Timed-сессия сбрасывается и не восстанавливается.

**SCENARIO-006 — Ошибка старта**
- Если нельзя создать сессию, таймер не стартует и используется существующая ошибка старта FEATURE-001.

## Business rules

- **BR-001.** Timed-режим дополнительный; ordinary-режим сохраняется.
- **BR-002.** Timed-сессия не имеет заранее заданного лимита по количеству примеров.
- **BR-003.** Длительность равна ровно 60 000 ms.
- **BR-004.** После каждого принятого ответа до дедлайна должен быть доступен следующий пример без дополнительного подтверждения.
- **BR-005.** Timed-сессия завершается только по дедлайну или технической ошибке, но не по достижению количества решенных задач.
- **BR-006.** После дедлайна новые ответы не принимаются.
- **BR-007.** Частично введенный ответ на дедлайне отбрасывается.
- **BR-008.** Внутри одной timed-сессии задачи должны быть уникальными, пока не исчерпан пул выбранного класса; после исчерпания пула допускается новый цикл выборки.
- **BR-009.** В timed-режиме не показывается правильность после каждого ответа.
- **BR-010.** Reload сбрасывает сессию.

## Validation and errors

- Старт доступен только после выбора класса и режима.
- Сохраняются текущие правила ввода ответа FEATURE-001.
- Submit после дедлайна отвергается независимо от визуального таймера.
- Повторные timeout callbacks после завершения идемпотентны.
- Если следующий пример невозможно получить из-за повреждения каталога, сессия завершается технической ошибкой и не должна показывать ложный пользовательский результат.

## Functional requirements

### FR-001 Выбор режима
- Description: До старта пользователь явно выбирает ordinary или timed.
- Priority: Must.

### FR-002 Неограниченная последовательность задач
- Description: Timed-сессия не ограничивается десятью задачами. После каждого принятого ответа до дедлайна приложение выдает следующую задачу.
- Priority: Must.
- Dependencies: FR-001.

### FR-003 Выбор задач без повторов до исчерпания пула
- Description: В рамках timed-сессии уже показанная задача не должна повторяться, пока доступен хотя бы один еще не показанный элемент пула выбранного класса. После полного исчерпания пула начинается новый цикл выборки.
- Priority: Must.
- Dependencies: FR-002, каталог FEATURE-001.

### FR-004 60-секундный абсолютный дедлайн
- Description: Дедлайн равен `startedAt + 60 000 ms` и определяется по реальному времени, а не числу timer ticks.
- Priority: Must.

### FR-005 Видимый таймер
- Description: Во время timed-сессии постоянно отображается оставшееся время, не ниже нуля.
- Priority: Must.
- Dependencies: FR-004.

### FR-006 Автозавершение по таймауту
- Description: При `now >= deadline` сессия автоматически и ровно один раз завершается без пользовательского подтверждения.
- Priority: Must.
- Dependencies: FR-004.

### FR-007 Семантика submit на дедлайне
- Description: Ответ засчитывается только если submit обработан при `now < deadline`; иначе ответ отбрасывается и сессия завершается по timeout.
- Priority: Must.
- Dependencies: FR-004, FR-006.

### FR-008 Итоговый результат
- Description: После timeout приложение показывает минимум количество правильных ответов и количество решенных примеров за 60 секунд. Формат должен позволять однозначно понять оба числа.
- Priority: Must.
- Dependencies: FR-002, FR-006, FR-007.

### FR-009 Повтор timed-сессии
- Description: «Еще раз» запускает новую независимую timed-сессию с тем же классом и режимом; возврат к выбору позволяет изменить класс или режим.
- Priority: Must.

### FR-010 Совместимость ordinary-режима
- Description: Ordinary-режим продолжает работать как FEATURE-001: 10 задач, без общего таймера.
- Priority: Must.

### FR-011 Accessibility
- Description: Таймер доступен программно, но обновление каждую секунду не создает непрерывный live-announcement; событие «Время вышло» объявляется.
- Priority: Must.

### FR-012 Analytics
- Description: Телеметрия различает ordinary/timed, completion reason и передает итоговые агрегаты timed-сессии без выражений и введенных ответов.
- Priority: Should.

## Acceptance criteria

- **AC-001 / FR-002:** Given timed-сессия активна и пользователь уже решил 10 задач до 60 секунд, when он отправляет 10-й ответ до дедлайна, then сессия не завершается и показывает 11-й пример.
- **AC-002 / FR-002:** Given timed-сессия активна, when каждый ответ принимается до дедлайна, then новый пример появляется без дополнительного действия и количество решенных может быть больше 10.
- **AC-003 / FR-003:** Given в текущем цикле пула есть непоказанные задачи, when запрашивается следующий пример, then ранее показанная в этом цикле задача не выбирается.
- **AC-004 / FR-004, FR-005:** Given timed-сессия стартовала в T0, when проходит 25 секунд, then UI показывает приблизительно 35 секунд остатка, вычисленных от абсолютного дедлайна.
- **AC-005 / FR-006:** Given пользователь ничего не делает, when `now >= T0+60s`, then результат показывается автоматически без submit.
- **AC-006 / FR-007:** Given ответ набран, when submit обрабатывается при `now >= deadline`, then он не увеличивает solved/correct.
- **AC-007 / FR-008:** Given к timeout принято 17 ответов, 14 из них правильные, then результат однозначно показывает `14 правильных` и `17 решено` (или эквивалентный формат с обоими числами).
- **AC-008 / FR-009:** Given timed-результат показан, when пользователь нажимает «Еще раз», then стартует новая 60-секундная сессия со счетчиками 0/0.
- **AC-009 / FR-010:** Given ordinary-режим выбран, when решено 10 задач, then он завершается как FEATURE-001 и никакой 60-секундный timeout к нему не применяется.
- **AC-010 / FR-011:** Timer ticks не объявляются screen reader каждую секунду; timeout announcement доступен.

## Analytics / telemetry expectations

- `session_started`: добавить `mode=ordinary|timed`.
- `answer_submitted`: для timed можно передавать порядковый номер принятого ответа, но не expression/entered answer.
- `session_completed`: добавить `mode`, `completion_reason=completed_all|timeout`, а для timed — агрегаты `solved_count`, `correct_count`, `duration_ms`.
- Сохраняются существующие правила allowlist и analytics policy.

## Non-functional expectations

- Дедлайн не должен зависеть от стабильности `setInterval`.
- Завершение сессии должно быть идемпотентным.
- Ordinary-режим не должен получить новый timer dependency.
- UI остается usable на текущих mobile widths.

## Assumptions

- **ASSUMPTION-001.** Timed-режим дополнительный.
- **ASSUMPTION-002.** Итог должен показывать как минимум correct_count и solved_count; это наиболее прямое отображение результата для неограниченного числа задач.
- **ASSUMPTION-003.** Задачи уникальны до исчерпания пула, затем разрешается новый цикл.
- **ASSUMPTION-004.** Countdown начинается при активации первого timed-задания после успешного session creation.

## Open questions

- **Q-001.** Подтвердить формат/семантику результата: `правильно X / решено Y` (оба показателя), а не `X из 10`.
- **Q-002.** Подтвердить правило уникальности задач до исчерпания пула и новый цикл после исчерпания.
- **Q-003.** Подтвердить, что режим timed сосуществует с ordinary.
- **Q-004.** Подтвердить момент старта countdown: первый timed-task активен после успешного создания сессии.
